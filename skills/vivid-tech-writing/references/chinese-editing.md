# 中文特化：先去掉翻译腔

余光中在《论中文的常态与变态》里有一段话，几乎就是为技术写作写的：

> 中文本来说是「因此」，现在不少人却爱说「基于这个原因」；本来说是「问题很多」，现在不少人却爱说「有很多问题存在」。对于这种化简为繁、以拙代巧的趋势，有心人如果不及时提出警告，我们的中文势必越变越差。

文章里还有一个更典型的例子：

> 作为公安部门，对于盗版行为，必须予以打击。

这句话没有一个字是错的，但它绕了三道弯：介词结构（作为……）、介词结构（对于……）、虚动词（予以）。中文的常态是“公安部门必须打击盗版”。

技术中文的翻译腔，通常不是英语造成的，是“怕不严谨”造成的。你越怕说错，越容易写成一团名词。

## 五种常见病

| 病 | 常见写法 | 改成 |
|---|---|---|
| 空动词 | 对缓存命中率进行了优化 | 把命中率从 62% 提到 91% |
| 抽象后缀 | 系统具有较高的可维护性 | 改一行代码不用动三个文件 |
| 被动 | 该问题被认为 / 通过实验可以证明 | 我们认为 / 我们做了三组实验 |
| “的”字链 | 基于用户行为数据的分析结果 | 我们看了 10 万次点击，发现 |
| 连接词冗余 | 由于网络抖动，因此导致请求超时 | 网抖了一下，请求超时了 |

共同的解药：**找到句子里真正干活的东西，让它当主语；找到真正的动作，让它当动词。**

## 十组改写

| 教材句 | 人话 |
|---|---|
| 对系统性能进行了优化。 | 接口 P99 从 800ms 降到 120ms。 |
| 索引可以显著提升查询性能，但会增加写入开销。 | 没索引时查一条要扫 200 万行；有了索引，3 行。代价是每次写入多维护一棵树。 |
| 该系统具有较高的可扩展性。 | 流量翻 10 倍，加两台机器就行，不用改代码。 |
| 由于网络抖动，导致请求超时。 | 网抖了一下，请求超时了。 |
| 用户对界面的满意度得到了提升。 | 改版后，点“下一步”的人多了 18%。 |
| 需要注意的是，该方案存在一定的局限性。 | 这个方案有一个硬伤：它假设所有机器时钟一致。 |
| Transformer 的自注意力机制通过计算 Query 和 Key 的相似度来聚合 Value。 | 你在派对上听人说话：耳朵扫过全场，谁的声音和你关心的对上，谁的内容就被放大。注意力机制干的就是这件事。 |
| 该算法的时间复杂度为 O(n log n)。 | 数据翻一倍，耗时大约多一倍再拐个弯；多出来的那个弯，就是 log n。 |
| 我们对该系统进行了重构。 | 我们把 3000 行的单文件拆成了 12 个模块，改一个功能不用再读完全部代码。 |
| 本文提出了一种新的方法。 | 我们试了三种办法，前两种都失败了。第三种，把问题反过来想，成了。 |

## 术语四条规矩

1. **先经验，后命名。** 先让读者看见“四个核心四份缓存”，再告诉他这叫“缓存一致性”。
2. **一次一个。** 一段只引入一个新术语。新术语出现后，立刻给例子，不要连续定义。
3. **三次才缩写。** 一个词在文章里出现三次以上，才值得缩写；否则读者要记两套名字。
4. **不用术语解释术语。** 如果必须用，先用类比把结构搭好，再补术语。

## 标点与节奏

- **句号是呼吸。** 一个句子超过 45 个字，读者就要回头找主语。回头一次，注意力就断一次。
- **少用“此外、然而、值得注意的是、综上所述”。** 它们不是逻辑，是缓冲垫。删掉之后，逻辑反而更清楚。
- **破折号是调味品，不是主食。** 一段最多一个。中文里的破折号用多了，会有一股翻译腔。
- **冒号后面给具体内容。** “原因如下：”后面不要接“存在多个方面”，要接“第一，缓存没命中；第二，锁等了 200ms”。
- **能用一个动词，不用“进行 + 名词”。**

## 病文重写：微服务

教材版：

> 微服务架构是一种将单一应用程序划分为一组小型服务的架构风格。每个服务运行在独立的进程中，通过轻量级的通信机制进行交互，并可以独立部署和扩展。该架构具有提高系统可维护性和可扩展性的优势，但也增加了分布式系统的复杂性。

重写：

> 一个 20 万行的单体应用，改一个按钮，要发一次全量发布；一个人写错，全站跟着挂。
>
> 微服务干的事，就是把它拆成十几个能各自发布的小服务：用户服务挂了，订单服务还能接单。
>
> 代价是：以前一次函数调用，现在变成一次网络请求。网络会超时、会重试、会重复扣款。你换来的不是“更先进”，是“坏事只坏一部分，但坏事的花样变多了”。

注意最后一句：它没有用“优点 / 缺点”这种教材结构，而是把代价写成了一个**有画面的判断**。读者可能不同意，但会记住。

## 翻译腔自检清单

改完中文，逐条扫：

- [ ] 有没有“进行/实现/完成/得到/加以/予以 + 名词”？
- [ ] 有没有“对……进行……”“对于……而言”“作为……”开头？
- [ ] 有没有连续两个“的”？
- [ ] 有没有“被”字句，但施事者其实可以说出来？
- [ ] 有没有“此外/然而/值得注意的是/综上所述”可以删？
- [ ] 有没有“性/化/度”可以换成具体结果？
- [ ] 有没有一句话超过 45 字？
- [ ] 有没有一段出现三个以上新术语？
- [ ] 读出声，有没有喘不过气的地方？

## 和 style_lint.py 配合

linter 会统计：名词化、被动、套话连接词、抽象后缀、长句、数字、人称、问句。

- 名词化/被动多：先看示例，挑最像“翻译腔”的三处改。
- 抽象后缀多：不一定是错（“复杂度”“吞吐量”是术语），看是否可以用具体结果替代。
- 数字为 0：确认文章是不是真的不需要数字；技术文章通常至少有一个可验证的量。
- 第二人称为 0：确认是不是 API 文档/规范；如果是博客，考虑加一个“你”。

不要把 linter 当评分。它只告诉你“哪里值得看一眼”。
