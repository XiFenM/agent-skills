# 诊断：七个病灶与病文会诊

诊断不是打分。下面每一条都是“信号”，不是“判决”：技术文档、法规、论文需要更多名词化和被动，这些场景不该硬改。先判断体裁，再决定要不要动手术。

## 先看一段标准教材体

> 缓存一致性是指在多核处理器系统中，多个处理核心的私有缓存之间保持数据一致性的机制。当某一核心对其私有缓存中的数据进行修改时，需要通过总线嗅探或目录协议等方式通知其他核心，以保证系统对外表现出单一共享存储器的语义。

这段话没有错，甚至很严谨。但它有三个问题：没有人物、没有后果、没有“为什么现在要说这个”。读者看完只记住一个名词，不知道它解决的是“四个核心四份缓存，A 改了 B 还读旧值”的麻烦。

## 七个病灶

| # | 病灶 | 长什么样 | 读者的真实感受 | 手术 |
|---|---|---|---|---|
| 1 | 名词化 | “对性能进行了优化”“实现了提升” | 动作被抽干，句子变重 | 找到被藏起来的动词，请回主语后面 |
| 2 | 无主语 | “该问题被认为”“通过实验可以证明” | 不知道是谁做的，也不太信 | 写“谁做的/谁测的/谁决定的” |
| 3 | 抽象悬空 | 从定义到定义，没有例子 | 每个字都懂，连起来不知道在说什么 | 先给一个具体例子/场景，再给定义 |
| 4 | 信息平权 | 每句都一样重，没有主次 | 读完不知道哪句重要 | 标出“如果只记一句”，其余降级或删 |
| 5 | 零悬念 | 结论先行，没有冲突 | 没有继续读的理由 | 先写困境/反常识，再给结论 |
| 6 | 术语前置 | 先给名字，再给经验 | 记不住，也不想记 | 先经验后命名；一段只引入一个新术语 |
| 7 | 没有“我/你” | 全篇第三人称、被动、客观 | 像说明书，不像人话 | 加一次判断、失败、偏好或对话 |

## 1. 名词化：把动作变成石头

| 教材句 | 人话 |
|---|---|
| 对缓存命中率进行了优化。 | 我们把缓存命中率从 62% 提到了 91%。 |
| 系统性能得到显著提升。 | 接口 P99 从 800ms 降到了 120ms。 |
| 对该模块实施了重构。 | 我们把 3000 行的单文件拆成了 12 个模块。 |
| 对用户反馈进行了分析。 | 我们看了 10 万条反馈，发现 60% 都在说同一个按钮。 |

名词化的标志很好认：**进行、实现、完成、得到、加以、予以 + 一个名词**。这个结构会把本来应该由动词承担的动作，塞进一个抽象名词里，句子的力量就漏光了。

手术：谁，做了什么，结果是多少。

## 2. 无主语：把作者藏起来

- “该问题被认为是一个性能瓶颈。” → “我们压测了三次，确认瓶颈在数据库连接池。”
- “通过实验可以证明该假设。” → “我们做了 A/B 两组实验，B 组快了 37%。”
- “相关方案已被采用。” → “我们上线了方案 B，因为方案 A 的回滚成本太高。”

无主语不一定是错。真正的问题是：**读者不知道谁对这件事负责，也就不知道该不该信。** 技术判断尤其需要“谁测的、什么条件、多大样本”。

## 3. 抽象悬空：从定义到定义

“索引是一种数据结构，用于加速数据检索。”

这句话对，但它没有钩子。读者脑子里没有“慢”的体验，就不会对“快”产生感觉。

换一个顺序：

> 1000 万行数据，查一条记录，40 分钟。加一个索引，3 毫秒。为什么差这么多？

先让读者站进“慢”里，再给他“快”。**术语是压缩包，你得先让读者看见解压后的内容，再告诉他这个压缩包叫什么。**

自检：这一段能不能被一个没学过这个术语的人复述？如果他只能重复名词，说明你还没解释。

## 4. 信息平权：每句都想重要

教材式段落常常每句一样长、一样重，读者读完不知道哪句是“主心骨”。

手术：

- 找出“如果读者只记一句，应该是哪句”，把它单独成段或加粗。
- 把“背景/例外/实现细节”降到从句、脚注或下一节。
- 一段只推进一步；不要在一段里同时做定义、举例、对比和总结。

## 5. 零悬念：把答案直接放在开头

教材的逻辑是“结论 → 论证”，故事的逻辑是“困境 → 尝试 → 转折 → 结论”。

不要写：

> B+ 树适合做数据库索引，因为它具有较低的树高和良好的范围查询性能。

试着写：

> 1000 万行数据，查一条要 40 分钟。加个索引，3 毫秒。可索引本身也是一棵树——二叉树不行吗？哈希不行吗？为什么偏偏是 B+ 树？

同一个结论，第二种写法让读者带着问题往下走。**问题是最好的目录。**

## 6. 术语前置：先给名字，再给经验

- 差：本文讨论“写时复制（Copy-on-Write）”。
- 好：两个进程读同一份数据，谁都不改，就共享；一旦有人要写，先复制一份再改，别动原来那份。这个做法叫写时复制。

规则：

1. 先经验，后命名。
2. 一段只引入一个新术语。
3. 一个词出现三次以上才缩写。
4. 不用术语解释术语；必须用时，先用类比把结构搭好。

## 7. 没有“我/你”：文章没有体温

不是每篇文章都要第一人称。但技术文章里适度的“我/我们”能提供三样东西：

- **判断**：“我更喜欢 B，因为回滚成本更低。”
- **失败**：“我们一开始也选错了，原因是……”
- **在场**：“我盯着这个火焰图看了半小时，才发现……”

如果体裁不允许第一人称（API 文档、规范、事故报告），至少给“你”一个位置：读者下一步要做什么，会看到什么，卡住时怎么办。

## 病文会诊：把“缓存一致性”重写一遍

原句（本节开头那段）的问题：

- 主语是“缓存一致性”这个抽象名词，不是人，也不是硬件。
- 动作全被名词化：“进行修改”“保持”“通知”“保证”。
- 一段至少五个术语：多核处理器、私有缓存、总线嗅探、目录协议、单一共享存储器。
- 没有后果：读者不知道“不一致”会怎样。
- 没有场景：哪个核心、什么数据、什么时候。

重写：

> 四个核心，四份缓存。核心 A 把变量 x 改成了 1，核心 B 的缓存里还躺着 x=0。如果 B 现在去读，它该读到什么？
>
> 读 0，程序就疯了；读 1，B 怎么知道 A 改过？
>
> 缓存一致性协议就是干这个的：谁改了数据，得喊一嗓子，让别人的副本作废。喊的方式有两种：一种是所有人都听总线（总线嗅探），一种是查通讯录（目录协议）。

信息一点没少，但读者先看见了“四份缓存”，再看见了“冲突”，最后才拿到两个术语。顺序变了，理解成本就降了。

## 用 style_lint.py 做初筛

有草稿文件时，先跑：

```bash
python scripts/style_lint.py draft.md
python scripts/style_lint.py --json draft.md
cat draft.md | python scripts/style_lint.py -
```

它统计：中文字符、句子长度、长句、名词化、被动、套话连接词、抽象后缀、数字/单位、第二人称、第一人称、问句、术语密度（`--terms`）。

**怎么读结果**：

- 它是信号，不是评分。不要对用户说“你的文风 62 分”。
- 先看“长句示例”和“名词化示例”，这些是最容易改的。
- 技术文档里被动和名词化可能合理；先问体裁，再建议改。
- 数字、人称、问句为 0 不一定是错；先确认这篇文章需不需要它们。

## 诊断输出模板

```markdown
## 一句话判断
[最要命的一个问题]

## 诊断表
| 病灶 | 原文证据 | 手术 |
|---|---|---|
| 名词化 | “对……进行了优化” | 改成“从 A 到 B” |
| ... | ... | ... |

## 三个优先动作
1. [先改哪里，为什么]
2. ...
3. ...

## 可选：改写示范
[只改一段，不超过 150 字]
```

诊断阶段默认不改全文。先让用户同意手术方案，再进入 `rewrite`。
