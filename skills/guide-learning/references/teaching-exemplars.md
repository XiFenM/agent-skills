## 示例一：MoE 与专家并行（系统概念课）

### 开课导入

> 稠密模型想变强，参数就得变多，而每个 Token 的计算量随参数同比增长。MoE 把 FFN 换成许多个专家，每个
> Token 只激活其中少数几个：总参数上去了，单个 Token 的计算量基本不变。代价转移到了系统侧——专家权重放不进
> 一张卡；Token 要被送到它选中的专家所在的卡上算完再送回来；哪个专家被选中由数据决定，负载天然不均。
> 这一课要解决的就是这个矛盾：专家怎样分布到多张卡上，Token 怎样高效地送过去、收回来，负载不均会卡在哪里。
>
> 学完你应该能：画出一个 MoE 层从路由到合并的完整数据流；解释大规模部署为什么普遍用 EP 而不是用 TP 切开
> 专家；估算一次 dispatch 与 combine 的通信量；判断一个没见过的部署方案会在哪里遇到瓶颈，并在面试中用一分半钟
> 讲清这些取舍。
>
> 全流程骨架，后面每个节点都会回到这张图：
>
> ```text
> X[T,H] → router：每个 Token 的 top-k 专家与权重
>        → 按专家重排（permute）
>        → dispatch：All-to-All 把 Token 向量送到专家所在的卡
>        → 各卡对本地专家做 grouped GEMM
>        → combine：All-to-All 把专家输出送回
>        → 按原 Token 加权求和 → Y[T,H]
> ```
>
> 路线：路由与门控 → 重排与还原 → dispatch 与 combine 的通信 → EP 与 TP 的取舍 → 负载均衡与真实部署。
> 完成标准：能对着这张图讲清每一步传什么、为什么这样设计，并对一个没讲过的部署判断通信和负载的变化。

### 节点讲解：为什么大规模 MoE 用 EP，而不是用 TP 切开每个专家

> 现在要把一个 MoE 层放到多张卡上：全部专家权重已经放不进一张卡，但每个 Token 只会访问路由选中的专家。
> 我们比较两种分工：把每个专家切成多片，还是把完整的专家分配给不同的卡。先沿着一个 Token 的计算看每张卡
> 负责什么，再比较这种分工带来的矩阵形状、通信和负载变化。
>
> **机制**：TP 把每个专家的 gate 和 up 权重按中间维切列、down 权重切行，每张卡对所有 Token 计算所有专家的
> 一片，最后对 [T,H] 的部分和做 AllReduce。EP 把完整的专家分给不同的卡，每张卡只计算被路由到本地专家的 Token。
>
> **为什么这样设计**：MoE 的专家通常又多又窄。以 DeepSeek-V3 为例：隐藏维度 7168，每个路由专家的中间维度
> 只有 2048，每层 256 个路由专家加 1 个共享专家，每个 Token 激活 8 个。用 TP=8 切开后，每张卡上每个专家的
> GEMM 只剩 256 列，矩阵单元吃不饱；EP 保留完整的 2048 列。配合 Attention 的 DP，每张卡处理不同的请求，每个
> 专家汇聚所有卡路由给它的 Token，GEMM 的行数随全局并发增长；Attention 部分也不再需要每层的 TP 通信。
>
> **真实系统**：代价落在通信上。一个 Token 的隐藏向量在 BF16 下约 14 KB（7168 × 2 字节）；top-8 意味着最多
> 要送往 8 个专家（按目标卡去重的实现中，同一张卡只收一份），combine 再收回来一遍。DeepSeek-V3 在训练中限制
> 每个 Token 最多路由到 4 个节点，以压低跨节点流量；DeepEP 分别提供面向训练和 prefill 的高吞吐内核，以及
> 面向 decode 的纯 RDMA 低延迟内核。来源：DeepSeek-V3 技术报告 arXiv:2412.19437 v1；DeepEP 仓库 README。
>
> **边界**：EP 的收益依赖足够大的并发和足够快的互联——每个专家要攒到足够多的 Token，All-to-All 的开销才能被
> 摊薄；单机、小批量或专家较少时，TP 或复制专家可能更简单也更快。负载不均时，整层延迟由最热的那张卡决定，
> 需要负载均衡策略或冗余专家。
>
> **本节归纳**：EP 让每个专家在一张卡上完整计算，只搬运被选中的 Token；TP 则把每个专家再切窄，并且每层要对
> 全部 Token 做 AllReduce。专家多而窄时，EP 的计算效率更高，还能让 Attention 改用 DP；代价是不规则的
> All-to-All，以及由路由决定的负载不均。
>
> **面试怎么讲**（约 60 秒）："MoE 的专家通常多而窄。用 TP 切专家，每张卡上的 GEMM 更窄，而且每层都要对全部
> Token 做 AllReduce；用 EP，每个专家在一张卡上完整计算，还能汇聚所有卡发来的 Token，Attention 也可以改成 DP。
> 代价是 All-to-All：流量随 top-k 增长、形状不规则，而且负载由路由决定，最热的卡决定尾延迟。所以大规模部署
> 用 EP，并配合限制跨节点路由、冗余专家和专门的通信内核来控制这两项代价。"

### 检查题：弱与强

| 弱：只考计算或记忆 | 强：考理解 |
| --- | --- |
| "按表格算出 dispatch 的字节数。"（只要求得数） | "估算 DeepSeek-V3 规模下每张卡处理 128 个 Token 时，单层 dispatch 要发送的数据量；再说明 prefill 和 decode 对通信内核的要求为什么不同。" |
| "t2 对应打包结果的第几行？" | "EP 部署下某一层的延迟明显高于其他层。最可能的两个原因是什么？分别用什么证据区分？" |

以诊断题为例，判对标准：能指出负载不均（看各专家或各卡收到的 Token 数）和通信瓶颈（看 All-to-All 的耗时
占比与跨节点流量）两类原因，并说出区分它们的观测量。

## 示例二：分块 softmax 与 FlashAttention 前向（算子课）

### 全流程骨架

> 单头简化。输入 Q、K、V 的形状都是 [N,d]，N 是序列长度，d 是头维；输出 O 的形状是 [N,d]。
>
> 未优化的数学：S = QKᵀ ÷ √d，形状 [N,N]；P = 按行 softmax(S)；O = PV。
>
> 朴素实现要把 N×N 的 S 和 P 写回 HBM 再读出来。N 较大时，这部分读写和显存占用随 N² 增长，成为瓶颈，而
> 矩阵乘本身的算力并不紧张。FlashAttention 要解决的矛盾是：softmax 需要整行信息（分母），片上存储却放不下
> 整行。
>
> 分解（FlashAttention-2 的划分）：按 Q 的行块分给不同的线程块，每个线程块负责一组输出行，在块内沿 K、V 的
> 列块循环。每行维护三样状态：当前最大值 m、当前指数和 ℓ、未归一化的输出累加 acc。循环结束时
> O = acc ÷ ℓ，并为反向保存每行的 L = m + log ℓ。
>
> 精度：Q、K、V 以 BF16 或 FP16 存储；S、m、ℓ 和 acc 在 FP32 中计算和累加，最后把 O 转回输入精度。

### 节点讲解：在线 softmax 为什么要保留两个统计量

> 现在沿着一行注意力分数处理数据，每次只读入一个分数块 S_j。完整一行的最大值还不知道，但前面读过的块
> 已经产生了需要保留的累加结果；新块还可能出现更大的分数。问题是：怎样让前后各块的结果始终使用一致的
> 指数基准，并在最后得到整行的归一化结果？
>
> **机制**：先为这一行记录三个状态：已经见过的最大值 m、以它为基准的指数和 ℓ，以及尚未归一化的输出累加 acc。
> 处理新块 S_j 时：
>
> ```text
> m_new   = max(m, rowmax(S_j))
> ℓ_new   = exp(m − m_new) · ℓ   + rowsum(exp(S_j − m_new))
> acc_new = exp(m − m_new) · acc + exp(S_j − m_new) · V_j
> ```
>
> 旧的 ℓ 和 acc 都以旧的 m 为基准；乘上 exp(m − m_new)，就换到了新基准。
>
> **为什么这样设计**：减去最大值是为了数值稳定——指数对较大的输入会迅速溢出（FP32 在输入约 88 时溢出，FP16
> 约 11 时就溢出），减去行最大值后所有指数都不超过 1。但最大值要看完整行才知道，所以需要"先用当前最大值，
> 之后再修正"的在线规则。只保留 m 不够：没有 ℓ 就无法归一化；只保留 ℓ 也不够：没有 m，就无法把不同块的指数
> 换到同一基准。
>
> **真实系统**：反向传播需要 P，但保存 N×N 的 P 正是前向想避免的。FlashAttention 只为每行保存
> L = m + log ℓ，只占 O(N) 空间；反向按块重算 S，再用 P = exp(S − L) 恢复概率——用重算换显存和带宽。来源：
> FlashAttention 论文 arXiv:2205.14135；FlashAttention-2 论文 arXiv:2307.08691。
>
> **边界**：块大小受片上存储和寄存器限制，头维 d 越大，每块能放的行越少；因果掩码下完全被遮住的块可以直接
> 跳过。这些改变性能，不改变数学结果；浮点累加顺序不同，逐位结果可能有微小差异。
>
> **本节归纳**：分块处理一行时，保留当前最大值 m 和指数和 ℓ，就能在看到新块后把之前的结果换算到新的最大值
> 基准上；输出累加 acc 同步换基准，整行处理完后再归一化。这样不必保留整行分数，也能得到对应的注意力输出。
>
> **面试怎么讲**："FlashAttention 不减少计算量，而是减少 HBM 读写：它从不把 N×N 的注意力矩阵写回显存。做法是
> 分块加在线 softmax——每行只维护最大值和指数和，看到新块时把旧结果缩放到新的最大值基准。反向时只保存每行
> 的 logsumexp，按块重算注意力矩阵，用计算换带宽和显存。"

### 检查题：迁移到两张卡

> 把序列切到两张卡上做 Attention，各自按同一规则得到局部状态。怎样合并结果？需要交换哪些量，为什么？

应先把两边的指数和与输出累加换到共同的最大值基准，再相加、归一化；题目检验状态含义与迁移，不重复考查表算数。

## 主例与分支：从关闭代码看等待关系

这里单独观察已接受一批数据后的收尾，不再提交新批。主线程持有只读数组 B、互斥锁 m、关闭标志 closing 和占用
标志 reading；consumer 同步读 B，再持 m 将 reading 改为 false。sum 只由 consumer 写，主线程在 join 后才检查它。

### 主例：先释放锁，再等待 consumer 退出

下面是 C++20 结构示例。closing 只标出关闭请求的发布位置，不在这段收尾代码中实现新批次准入。

```cpp
#include <array>
#include <mutex>
#include <thread>

int main() {
    const std::array<int, 4> B{1, 2, 3, 4};
    std::mutex m;
    bool closing = false, reading = true;
    int sum = 0;
    std::thread consumer([&] {
        for (int x : B) sum += x;
        std::lock_guard lock(m);
        reading = false;
    });

    {  // 关闭请求的临界区
        std::lock_guard lock(m);
        closing = true;
    }
    consumer.join();
    return closing && !reading && sum == 10 ? 0 : 1;
}
```

- **锁何时释放**：主线程关闭临界区的右花括号结束 `lock` 的生命周期，析构负责释放 m；后面的 join 不持有 m。
- **谁还需要锁**：consumer 的循环结束后还要取得 m，才能更新 reading 并返回。读完 B 与线程已经退出是两个时刻。
- **存储何时销毁**：B、m 和状态仍在 main 的作用域内；join 成功返回后，主线程才检查结果并离开这个作用域。

### 分支：只把 join 移入关闭临界区

只替换主例中“关闭请求的临界区”及紧随其后的 join，其他代码、对象与前提不变：

```cpp
    {  // 分支替换片段
        std::lock_guard lock(m);
        closing = true;
        consumer.join();
    }
```

考虑主线程先取得 m、consumer 随后读完 B 的这一条允许顺序：主线程在 join 等 consumer 返回；consumer 在
`std::lock_guard lock(m)` 等主线程解锁；主线程却要等 join 返回才能走到释放锁的右花括号。沿这两处代码就能看出等待环。

若 consumer 在主线程取得 m 前已经退出，这次分支可能返回，所以不能声称每次执行都会死锁。修正就是恢复主例的
作用域：主线程先释放 consumer 收尾所需的 m，再 join；不是禁止所有持锁时的 join，也没有必要另换线程或数据来解释。
这是按代码与同步规则分析的执行顺序，不冒充运行观察；展示运行结果时另附实际编译与受控执行记录。
