# Source authority

使用文档、教程、论文、示例或源码进行教学，核验版本敏感的事实，设计实验，或处理来源冲突时读取本参考。把
"按什么顺序讲"与"由谁裁决事实"分开。

## 1. 来源角色

用户选择的资料默认是教学主线（teaching spine），但它不自动裁决所有事实，也不因为找到另一份更顺手的资料就被
静默替换。为实际使用的来源记录：位置、角色、版本锚点、使用范围。

| 角色 | 裁决范围 |
| --- | --- |
| `teaching-spine` | 内容主线与例证；可以在既定目标内调整讲解顺序、补充脚手架，但不等于扩大采用范围或门槛 |
| `implementation-authority` | 固定版本的具体实现、数据流与控制流 |
| `interface-authority` | 公开接口、规范与承诺的语义 |
| `method-authority` | 论文或标准定义的方法、假设与报告结论 |
| `empirical-evidence` | 只在声明的环境、输入和测量边界内成立的观察 |
| `explanatory-support` | 教程、示例、类比或第三方解释；不覆盖一手来源 |

同一来源可以承担多个角色，分别说明适用范围。不复制大段正文，保存能重新定位证据的锚点。受管 context 中的事实
角色只是查找提示：资料目录不自动成为教学主线，知识产物不自动裁决事实，验证说明不自动定义完成门槛；学习者
偏好可以调整表达顺序和节奏，但不能降低证据要求。

## 2. 按主张类型选择权威

| 主张 | 首选权威 | 不能单独裁决 |
| --- | --- | --- |
| 某个版本的实现与控制流 | 固定 commit 或 tag 的源码 | 未固定版本的教程、记忆中的实现 |
| 公开 API 与保证 | 官方文档、规范、发布说明 | 示例代码、偶然的运行结果 |
| 论文方法、假设与报告数字 | 论文本身及补充材料 | 二手摘要、其他实现的 benchmark |
| 当前环境中的行为 | 明确版本与输入下的本地运行 | 其他设备或版本的结果 |
| 性能、设备或资源结论 | 可复现的实验与受控比较 | 测试通过、一次没有边界的计时 |
| 教学解释 | 用户选定的主线与合适的脚手架 | 不能覆盖上面各行的一手事实 |

区分四类陈述：**来源事实**（来源明确声明或代码直接显示）、**本地观察**（在给定环境实际复现）、**推断**（由事实
和观察推出但未被直接裁决）、**假设**（等待实验或进一步来源验证）。不要把推断写成来源原话，也不要把本地测试
通过说成通用保证。

## 3. 版本锚点

开始结构化 Lesson 时记录相关的 commit、tag、文档版本、论文版本或日期，足以让之后的会话判断来源是否漂移。

- 本地源码：仓库相对路径和 commit；有未提交修改时注明工作区边界。
- 官方文档：产品版本或发布日期；页面没有版本时才用访问日期。
- 论文：版本号、发布日期或稳定标识。
- 实验：软件、硬件和关键配置；不要把教学资料的日期当成实验环境。
- "当前""最新""现在支持"这类易变主张，在回答时重新核验，不沿用旧记录。

只读恢复不更新时间锚点；只有来源或采用范围实际变化时才更新。

## 4. 最小补充核验

以下任一情况成立时，主动做最小的补充核验：

1. 教学主线缺少当前节点必需的前置，包括关键 API 或数据类型的语义与约束；
2. 来源可能过时，或与目标版本冲突；
3. 关键结论需要一手来源裁决；
4. 目标要求比较、迁移或跨版本解释；
5. 讲解需要真实系统的锚点或规模数字，而主线没有提供。

不改变目标、范围和投入的最小核验可以直接做，标明来源角色即可。替换教学主线、纳入体量较大的新资料、扩大目标
或证据要求、明显增加投入或引入新依赖、把旁支研究变成新的前台任务之前，先取得用户确认。核验完回到主线，
不要让资料收集取代教学。

## 5. 冲突处理

1. 核对版本、分支、配置、平台、输入和适用条件。
2. 分别说明每个来源能支持和不能支持的主张。
3. 按用户的目标版本选择本课采用的行为，不用"多数票"揉成一个答案。
4. 能用最小的一手核验解决时就做，并记录来源角色；解决不了时标为待验证。
5. 只有冲突阻塞当前目标时才扩大调查；否则记为观察，回到主线。

冲突会改变目标、来源范围、责任或下一步动作时，让用户选择分支，不静默修改课程约定。注释、变量名与实际数据流
不一致时，明确指出差异并以实际实现为准；不要为了让教程显得合理，把未经证实的作者动机、实现必要性或性能收益
补成事实。

## 6. 实证结论的边界

- 结果出现前保存预期方向、依据、不确定性和可被推翻的条件。
- 记录环境、版本、输入、控制变量、命令或方法和测量范围。
- 使用与目标相称的基线或受控比较；功能正确性与性能测量分开。
- 说明证据支持什么、不能支持什么，以及剩余的不确定性。

测试通过只证明已覆盖的行为，不自动成为性能、设备或真实运行的结论；同时改变多个因素时，不把结果归因于其中
一个。跨设备、跨版本或跨工作负载的推广标为推断，除非有相应证据。

## 7. 在讲解中呈现来源与边界

- 教学主线要让学习者找得到：开课和每个节点都给出资料的位置与对应范围，做法见
  [teaching-cycle.md](teaching-cycle.md) 第 2、5 节。
- 核心结论直接说，来源和版本集中附在该段末尾一次；不要在每段前后堆叠"不能外推""不代表"之类的限定。
- 适用边界集中成一句，放在结论之后；只有会改变学习者判断的限定才写进正文。
- 推断明确标为推断，一次即可；不要用含糊的措辞代替明确的"已核验""推断"或"待验证"。
- 真实数字写清单位、条件和来源，让学习者能复核。

## 8. 与资料治理的分工

本 Skill 只为当前学习目标做最小的来源核验。广泛的资料候选池、周报、课程资料晋级和跨模块排序交给
`resource-planning`。学习中发现的长期资料只记为当前课程内的观察，或向用户提议交接；候选资料不自动改变教学
主线、稳定的课程资料或下一课，也不构成执行授权。
