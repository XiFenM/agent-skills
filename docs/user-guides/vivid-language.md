# Vivid Language / 生动语言

`vivid-language` 是一个无状态的语言层：它管 Agent 说出口的**所有**文字——回复、进度、提问、报错、总结，以及讲解、课程网页、记忆卡片、技术文章和视频口播稿——让这些话像一个人在说，而不是教材或客服机器人。默认只在对话里交付文本，不读写仓库里的学习记录、卡片、资源或发布状态。

它原名 `vivid-tech-writing`，重心在文章与视频写作；现在范围扩到全部输出，所以改名。文章和视频的写作工艺仍是它的一部分，只是不再独占。

一旦启用，它管的是当前这场对话里的全部输出，直到你说停或换回原来的语气；不是每写一段都要重新调用一次。

## 什么时候适合使用

- Agent 的回复太像客服：满屏"好的""收到""很抱歉给您带来不便""希望这对您有帮助"。
- 进度和总结让人抓不住重点：读了三段还不知道做完了没有、要不要自己做决定。
- 报错只贴一行栈，或者只写"操作失败"，不说影响和下一步。
- 你写了一篇技术文章，读起来像说明书：定义先行、全是"进行了优化"。
- 你要从零写博客、教程或分享稿，需要先搭一个不散的骨架。
- 你要把文章改成 60–90 秒口播稿，或直接写知识视频脚本。
- 你觉得讲解、课程页面、卡片文字太书面，希望更口语、更像日常聊天。
- 你想学方法，想要书单、样板、逐句拆解或 30 天练习。

不适合：

- API 参考、发布说明、法规、事故报告：这些走 clarity-first，不应该硬加故事和悬念。
- 纯校对、SEO、营销文案：不是这个 Skill 的目标。
- 需要事实核查、实验复现或代码审查：它可以标出"待核实"，但不替代这些工作。

## 两个坐标：场合与模式

**场合**决定文字长什么样、能开多大玩笑、允许多少铺垫。

| 场合 | 读的人在哪 | 默认 | 生动度 |
|---|---|---|---|
| 对话反馈 | 聊天窗里扫 | 1–3 句 | 直接、具体、不客套 |
| 工程书面 | commit / PR / 注释 / 报错 | 1 行说清 | 准确优先，不玩梗 |
| 教学讲解 | 边听边想 | 一段一个关系 | 高：场景 + 主例 + 比喻 |
| 课程网页 | 离线页面上读 | 一段约 220 字 | 高：像当面讲 |
| 记忆卡片 | 乱序单独看 | 一张一个目标 | 中：清晰完整，不要求口语 |
| 学习/技术文章 | 主动阅读 | 看承诺 | 高：2–3 个动作 |
| 视频口播 | 用耳朵听 | 30–45 秒一个变化 | 高：画面 + 因果 |
| 参考文档 | 查参数 | 最短可查 | 低：clarity-first |

**模式**决定这一次要做什么：

| 模式 | 你输入 | 它输出 |
|---|---|---|
| `diagnose` | 一段草稿 + "看看哪里枯燥/哪里像 AI" | 一句话判断、诊断表、三个优先手术；默认不改写 |
| `rewrite` | 草稿 + "改这一段/全文" | 改写、改了什么/为什么、待核实 |
| `draft` | 主题、读者、长度、约束 | brief、结构、初稿、待核实 |
| `video` | 文章或主题 + 时长/平台 | 口播稿、镜头表、待核实 |
| `coach` | "我想练""给我一个计划" | 一个概念、一个样板、一个练习、一次反馈 |

只给草稿、不指定模式时，它默认先做 `diagnose`，再问你要不要直接改写。

## 最常用的是对话

一句回复也算语言。默认形状是：

- **先给结论**：第一句就是结果、问题或判断。
- **给证据**：文件名、命令、数字、测试结果，不写"已完成"。
- **给下一步**：需要你决定时，只问一件事，并给默认方案。

例如，同样是汇报：

> 不要：好的，我已经了解了您的需求，现在正在为您处理中，请稍候。

> 改成：先换 `skills/` 里的 3 处旧名字，再跑全量测试。

报错时：

> 不要：抱歉，出现了一个错误，请稍后重试。

> 改成：`render.cjs` 在 Node 24 下报 `ERR_REQUIRE_ESM`：这个包只发 ESM。影响是页面写不进去；我改成动态 `import()` 再跑一次。你也可以先让我跳过渲染。

完整规则、八种对话动作和更多 before/after 在 [`references/conversation.md`](https://github.com/XiFenM/agent-skills/blob/main/skills/vivid-language/references/conversation.md)。

## 想更口语、更像日常

直接说：

> 把这段改得更口语、更像日常聊天，最好加一个生活里的比喻；数字和限定条件不要删。

Agent 会先给"一句话答案"，必要时补一张流程/阶段图，再用 2–3 个日常物件作比喻；每个比喻都会标"哪里不像"。它不会为了顺口删掉 caveat，也不会把 API 文档改成故事。

如果你只想要"诊断"，说"先别改，告诉我哪里太书面"即可；它会先给诊断表，再问要不要进入 `rewrite`。

## 跨体裁语言契约

`guide-learning` 的讲解、`lesson-pages` 的页面文字、`memo-cards` 的题面与答案、`english-coach` 的反馈，以及所有 Skill 的对话输出，共用同一套语言底线。完整契约在 [`references/language-contract.md`](https://github.com/XiFenM/agent-skills/blob/main/skills/vivid-language/references/language-contract.md)。

它管的是：先给可抓的东西，完整优先于短，一个主例贯穿，术语先定义，事实与推断分开，结论能自评，对话不客套、不流水账。它不管教学深度、页面结构、卡片等级与授权——那些仍由各自 Skill 负责。课程网页和记忆卡片在完成前会先让远程模型审查、失败时再交给子 Agent，按这份契约分别检查页面语言（口语化、生动）和卡片语言（清晰、完整）。

如果你在这些 Skill 里觉得文字太书面，也可以直接说"按 language-contract 的教学/课程网页/记忆卡片体裁改一下"。

## 想让它先过一遍更会说人话的模型

如果你当前的模型怎么调都还是教材腔，可以让 `vivid-language` 先把文字交给 ZenMux 上更会说中文的 Gemini 4 模型审查或改写，再回到这场对话里执行：

1. 在 [ZenMux 控制台](https://zenmux.ai/platform) 创建 API Key；
2. 在 shell 里 `export ZENMUX_API_KEY="sk-..."`，写进 `~/.zshrc` 后 `source` 一次；
3. 直接说“按 vivid-language 审一下这段”或“先别改，帮我诊断”。

Agent 会先跑远程审查：默认依次尝试 `google/gemini-4-neon`、`google/gemini-4-hydrogen`、`google/gemini-4-carbon`、`google/gemini-4-argon`，谁先回应就用谁。Key 被拒绝、或四个模型都不回应时，退回只读子 Agent；子 Agent 也没有时，自审并明确写“未独立审查”。想看哪些模型通，跑 `python3 <vivid-language>/scripts/zenmux_review.py --check`。

正文会通过 HTTPS 发到 ZenMux。没有 Key 时不发任何请求；不想外发时设置 `VIVID_LANGUAGE_REMOTE_REVIEW=off`。模型链可以用 `VIVID_LANGUAGE_ZENMUX_MODELS` 换成你自己的。完整说明见 Skill 的 `references/remote-review.md`。

## 一次典型交互

1. 你说明文本要去哪（对话、页面、卡片、文章、视频）、给谁看、必须保留什么。
2. Agent 最多问四个问题；能从草稿推断的，它会先说明假设，不审讯。
3. 它先找"一句话承诺"：读者读完能做什么、知道什么、改变什么。
4. 它选 2–3 个动作，不会九个全上；对话和卡片通常只用 0–1 个。
5. 它交付文本，并列出"改了什么/为什么"和"待核实"。
6. 你可以只接受其中一个动作，让它按那个动作再改一版。

## 你需要提供什么

- **草稿或要点**：哪怕只是几段烂初稿，也比"帮我写一篇"有用。
- **场合**：这是发在聊天里的回复、要贴在页面上的讲解，还是一篇文章？场合不同，长度和比喻密度不同。
- **读者**：谁会读，他们已经知道什么，读完后要能做什么。
- **不能动的东西**：数字、API 行为、结论、合规表述。
- **语气样本**：你以前的文章、口播、邮件或聊天；没有的话，明确说"用第一人称/不用第一人称"。
- **真实经历**：如果你想用"我犯过的错"开场，给它真实的那一次。Agent 不会替你编。

## 结果与边界

- **默认只在对话里交付**。不写入仓库、不发布、不改文件；需要保存时你明确说。
- **不编造**。事实、数字、引文、来源、个人经历，缺了就标 `[待核实]` 或向你要。
- **不歪曲**。为了画面做的简化会写明简化在哪、代价是什么；技术结论不被"生动"改变。
- **不硬套**。API 文档、发布说明、法规文本走 clarity-first，不加段子和悬念。
- **不客服腔**。不用"很抱歉给您带来不便""感谢您的耐心等待""希望这对您有帮助"。
- **不模仿签名句**。可以学结构动作，不复制在世作者的标志性措辞。
- **不俯视**。不用"小白也能懂""连我妈都会"；用"我曾经也不懂"。

## 和别的 Skill 的分工

- `creator-workflow`：多阶段、可恢复、需要授权与发布交接的内容生产。`vivid-language` 只负责"怎么讲"。
- `guide-learning`：教学、提问、练习、掌握度。`vivid-language` 不判断学习者是否掌握。
- `lesson-pages`：页面结构、布局、交互与文件。`vivid-language` 只管页面上的文字。
- `memo-cards`：卡片拆分、等级、身份与 Markji 格式。`vivid-language` 只管题面与答案的语言。
- `study-log` / `resource-planning`：学习记录、卡片、资源。`vivid-language` 不写这些状态。
- 需要把文章变成成片、剪辑、配音、发布：交给 `creator-workflow` 或对应的视频 Skill；这里只产出脚本和镜头表。

## 一个例子

改写前：

> 数据库索引是一种用于加速数据检索的数据结构。常见的索引类型包括 B+ 树索引、哈希索引和全文索引。合理使用索引可以显著降低查询的时间复杂度，但也会带来额外的存储和写入开销。

改写后：

> 图书馆里有一千万本书。你要找《三体》，管理员没有目录，只能一排一排翻——这就是全表扫描。
>
> 后来他给了你一个卡片柜，按书名排好。你拉开"三"字那一格，三秒钟找到。这就是索引。
>
> 但卡片柜不是白来的：每进一本新书，管理员都得多写一张卡。书进得越多，写卡越慢。
>
> 所以索引的真相是：你用"写的时候多干一点"，换"读的时候少等很久"。读多的表，值得；写多的表，想清楚。

## 怎么开始

直接给它一段你写的文字，并说清楚三件事：

1. 这段文字会出现在哪（聊天、页面、卡片、文章、视频口播）；
2. 这是给谁看的；
3. 哪些事实/数字不能动。

例如：

> 这是我给团队写的一篇缓存入门，读者是刚入职的后端。现在开头太像教材，帮我诊断，先别改。必须保留"四核四缓存"的例子和 800ms→120ms 的数字。

它会先给诊断，不会一上来重写全文。
