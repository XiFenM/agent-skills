# Vivid Tech Writing

`vivid-tech-writing` 是一个无状态的写作教练：它诊断、改写或起草技术博客、教程、技术分享稿和知识视频口播稿，让文章读起来像一个人在说话，而不是一本教材。默认只在对话里交付文本，不读写仓库里的学习记录、卡片、资源或发布状态。

## 什么时候适合使用

- 你已经写了一篇技术文章，但读起来像说明书：定义先行、全是“进行了优化”、读者不知道为什么要往下读。
- 你要从零写一篇博客、教程或分享稿，需要先搭一个不散的骨架。
- 你要把一篇文章改成 60–90 秒的口播稿，或者直接写一条知识视频脚本。
- 你想学方法，想要书单、样板、逐句拆解或 30 天练习。
- 你写的英文技术文章太绕，想改成更直接的表达。
- 你觉得文字太书面、太像教材，希望更口语、更像日常聊天，或者加一个生活里的比喻。

不适合：

- API 参考、发布说明、法规、事故报告：这些文本需要 clarity-first，不应该硬加故事和悬念。
- 纯校对、SEO、营销文案：不是这个 Skill 的目标。
- 需要事实核查、实验复现或代码审查：它可以标出“待核实”，但不替代这些工作。

## 五种模式

| 模式 | 你输入 | 它输出 |
|---|---|---|
| `diagnose` | 一段草稿 + “看看哪里枯燥” | 一句话判断、诊断表、三个优先手术；默认不改写 |
| `rewrite` | 草稿 + “改这一段/全文” | 改写、改了什么/为什么、待核实 |
| `draft` | 主题、读者、长度、约束 | brief、结构、初稿、待核实 |
| `video` | 文章或主题 + 时长/平台 | 口播稿、镜头表、待核实 |
| `coach` | “我想练”“给我一个计划” | 一个概念、一个样板、一个练习、一次反馈 |

如果你只给草稿、不指定模式，它默认先做 `diagnose`，然后问你要不要直接改写。

## 想更口语、更像日常

直接说：

> 把这段改得更口语、更像日常聊天，最好加一个生活里的比喻；数字和限定条件不要删。

Agent 会先给“一句话答案”，必要时补一张流程/阶段图，再用 2–3 个日常物件作比喻；每个比喻都会标“哪里不像”。它不会为了顺口删掉 caveat，也不会把 API 文档改成故事。

如果你只想要“诊断”，说“先别改，告诉我哪里太书面”即可；它会先给诊断表，再问要不要进入 `rewrite`。

## 一次典型交互

1. 你说明体裁、读者、长度、必须保留的事实，以及有没有过往文章可以作为语气样本。
2. Agent 最多问四个问题；能从草稿推断的，它会先说明假设，不审讯。
3. 它先找“一句话承诺”：读者读完能做什么、知道什么、改变什么。
4. 它选 2–3 个动作，不会九个全上。
5. 它交付文本，并列出“改了什么/为什么”和“待核实”。
6. 你可以只接受其中一个动作，让它按那个动作再改一版。

## 你需要提供什么

- **草稿或要点**：哪怕只是几段烂初稿，也比“帮我写一篇”有用。
- **读者**：谁会读，他们已经知道什么，读完后要能做什么。
- **不能动的东西**：数字、API 行为、结论、合规表述。
- **语气样本**：你以前的文章、口播或邮件；没有的话，明确说“用第一人称/不用第一人称”。
- **真实经历**：如果你想用“我犯过的错”开场，给它真实的那一次。Agent 不会替你编。

## 结果与边界

- **默认只在对话里交付**。不写入仓库、不发布、不改文件；需要保存时你明确说。
- **不编造**。事实、数字、引文、来源、个人经历，缺了就标 `[待核实]` 或向你要。
- **不歪曲**。为了画面做的简化会写明简化在哪、代价是什么；技术结论不被“生动”改变。
- **不硬套**。API 文档、发布说明、法规文本走 clarity-first，不加段子和悬念。
- **不模仿签名句**。可以学结构动作，不复制在世作者的标志性措辞。
- **不俯视**。不用“小白也能懂”“连我妈都会”；用“我曾经也不懂”。

## 和别的 Skill 的分工

- `creator-workflow`：多阶段、可恢复、需要授权与发布交接的内容生产。`vivid-tech-writing` 只负责“怎么讲”。
- `guide-learning`：教学、提问、练习、掌握度。`vivid-tech-writing` 不判断学习者是否掌握。
- `study-log` / `memo-cards` / `resource-planning`：学习记录、卡片、资源。`vivid-tech-writing` 不写这些状态。
- 需要把文章变成成片、剪辑、配音、发布：交给 `creator-workflow` 或对应的视频 Skill；这里只产出脚本和镜头表。

## 一个例子

改写前：

> 数据库索引是一种用于加速数据检索的数据结构。常见的索引类型包括 B+ 树索引、哈希索引和全文索引。合理使用索引可以显著降低查询的时间复杂度，但也会带来额外的存储和写入开销。

改写后：

> 图书馆里有一千万本书。你要找《三体》，管理员没有目录，只能一排一排翻——这就是全表扫描。
>
> 后来他给了你一个卡片柜，按书名排好。你拉开“三”字那一格，三秒钟找到。这就是索引。
>
> 但卡片柜不是白来的：每进一本新书，管理员都得多写一张卡。书进得越多，写卡越慢。
>
> 所以索引的真相是：你用“写的时候多干一点”，换“读的时候少等很久”。读多的表，值得；写多的表，想清楚。

## 怎么开始

直接给它一段你写的开头，并说清楚三件事：

1. 这是给谁看的；
2. 你希望读者读完后能做什么；
3. 哪些事实/数字不能动。

例如：

> 这是我给团队写的一篇缓存入门，读者是刚入职的后端。现在开头太像教材，帮我诊断，先别改。必须保留“四核四缓存”的例子和 800ms→120ms 的数字。

它会先给诊断，不会一上来重写全文。
